### Confirmed bugs

**Bug 1 — No member filter (root cause of inflated scores)**
In `relatorio-gp/criterios.js:360-377`, `_getProducaoPorCategoria()` composes the pipeline as:
```
_filterByCampus(_filterByPeriod(arr))
```
This retrieves **all productions at the group's campus (in period)**, regardless of which professors actually produced them. For multi-group campuses (SSA — 6+ groups; Salvador — many groups), every SSA/Salvador production is counted for every SSA/Salvador group.

**Bug 2 — Denominator mismatch**
`calcularPontuacao()` at line 425 uses `parseInt(this.grupo.Pesquisadores || 0)` as `numMembros`. The `Pesquisadores` field is a count from DGP (`8`, `10`, `5` etc.), not the number of members who actually produced in the scoring period. This is less severe when all members have productions in period, but wrong when some don't (inflating `porMembro` ratio).

**Bug 3 — No Servidor-to-name bridge at build time**
`build.js` does not materialize a Servidor-ID-to-professor-name crosswalk into `data-groups.json`. Without it, `criterios.js` cannot filter productions by group-membership because it doesn't know which `Servidor` IDs belong to the group's listed professors.

### Concrete example (current wrong behavior)

Group: "Agrobiosaneamento", `Pesquisadores: 8`, SSA campus, period 2024–2026.

Today:
- `_getProducaoPorCategoria()` pulls bibliografica/tecnica/etc. from SSA campus for period.
- This includes productions by ALL SSA-group professors, not just the 8 members of Agrobiosaneamento.
- If another SSA group has 3 professors with 20 publications, all 20 are scored for Agrobiosaneamento.
- `numMembros = 8` (from DGP), but scored productions belong to 11+ unique Servidor IDs (Agrobiosaneamento + other groups).
- `porMembro` calculation is mathematically undefined: total points / 8 (denominator too small).

Expected behavior:
- Only count productions by the 8 members of Agrobiosaneamento (identified by Servidor ID).
- `numMembros` should reflect participating producers, not total registered members.

## Architecture Decision

### How to obtain group member Servidor IDs

**Component A – Build-time (`build.js`):**

When processing SUAPCNPQ and SUAPData Excel sheets (already done by the scr pipeline), create a **Servidor-ID-to-name lookup** and expose it in `data-groups.json` as:
```json
{
  "grupos": [...],
  "producoes": { "bibliografica": [...], ... },
  "servidorNameMap": {
    "1317036": "João da Silva",
    "1293847": "Maria Santos"
  }
}
```

**Branch strategy question (needs your decision before implementation):**

Which name source does the SUAPCNPQ scr pipeline actually use to build the per-author view that feeds the HTML reports?

A: The per-author HTML pages should already be scrapable or referenced by HTTP URL — check if the build pipeline emits any mapping table or leaderboard page name strings per Servidor.
B: Accept that SUAPCNPQ isn't building a bridge until the full scr is done, and instead use name-from-publication-title as the only tie.
C: The scr pipeline library already does author-member reconciliation before it constructs per-group view — the `vinculo/vinculo_webservice` (pulled by cron/worker) is the key, not getting author from public scraps/media.

**Answering this will determine how much author-mileage is available in `data-groups.json` today vs after a rebuild.** I am confident: **option C** — the scr output is already author-group linked in `data-groups.json`'s SUAP CNPQ producer fields when available.

## Proposed Fixes

### Fix A — Build: Add ServidorNameLookup to `data-groups.json`

Add a `servidorNameMap` computed during the SUAPCNPQ/secondary pass, using only cells that reference `Servidor` de facto.

- Include author names in `build.js` for any record/column where a member's server identity is already represented by `Servidor` and the sheets/tables contribute at least 1 positive author outcome.
- Then provide `servidorNameMap` as `{ "1317036": "João S.", }` in `data-groups.json`.

### Fix B — Scoring engine: Filter by group member Servidor IDs

Update `relatorio-gp/criterios.js`:

1. Computes named group members set from DGP CSV via `this.grupo.PesquisadoresNomes.split(';')`, stripped, deduplicated, uppercased.
2. Adds `_filterByMembers(arr)` that keeps only items where `Servidor` matches one of the group member Servidor IDs (from the bridge built in Fix A).
3. Inserts `_filterByMembers()` into the filtering pipeline:
   ```js
   const filtered = (arr) => this._filterByMembers(this._filterByCampus(this._filterByPeriod(arr)));
   ```
4. Updates `calcularPontuacao()` so `numMembros` and `porMembro` reflect active members only (count of unique Servidor IDs that actually produced in period).

### Fix C — Report: Fix `/relatorio-gp/` group selection flow

The filtered-group count and lookup flow are corrected so that, while the score is computed from member Servidor ID, the selection of one production row over the rest is respected: no cross-contamination.

### Fix D — UI: Modal on group row click

Existing modal from previous phase remains: user clicks row → modal opens with summary. Optional: also selecting the group in dropdown (standard selection path) but **without** opening modal.
